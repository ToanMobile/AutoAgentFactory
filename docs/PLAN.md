Tên hiển thị của account: key `accounts.aliases` ở tầng 1 (xem §C.8); id của account không phụ thuộc tên.

### C.2 `tree_fp`, receipt, approval (`aaf-fp`, đã viết sẵn ở Wave 0)

- `tree_fp`: chép index thật sang file tạm trong git dir, `GIT_INDEX_FILE=<tạm> git add -A --sparse`, `git write-tree`. Kết quả `git-tree:<hash>`. Bao gồm file tracked và untracked không bị ignore; không đổi khi commit cùng nội dung. Không để lại gì trong repo: blob và tree mà git phải ghi đi vào một thư mục object tạm trong git dir (`GIT_OBJECT_DIRECTORY`, kho thật là `GIT_ALTERNATE_OBJECT_DIRECTORIES`), xoá sau khi tính; giá trị của một checkout thường không đổi so với cách tính cũ. Sparse checkout: `--sparse` để file nằm ngoài định nghĩa sparse nhưng có trên đĩa vẫn được tính (trước đây `git add -A` thoát 1); entry mà sparse checkout bỏ khỏi work tree giữ nguyên trong index, nên cây sạch vẫn bằng tree của HEAD. Cần git có `add --sparse` (từ 2.34).
- Dọn thư mục tạm còn sót (`aaf-fp/src/stale.rs`): file tạm là `aaf-index-<pid>-<n>` và `aaf-objects-<pid>-<n>` trong git dir; lượt bị SIGKILL để lại chúng (kèm blob của mọi file đổi và untracked). Mỗi lần tính `tree_fp`, entry mang tên đó mà pid đã chết bị xoá (symlink xoá như link); pid của chính tiến trình, pid còn sống, hay `ps` không trả lời được thì giữ nguyên; xoá lỗi thì bỏ qua, lần sau thử lại.
- File trên đĩa mà `tree_fp` không thấy (`aaf_fp::hidden_files`, `aaf-fp/src/hidden.rs`): (1) file tracked có trên đĩa mang cờ `skip-worktree`/`assume-unchanged` (`flagged`); (2) file chỉ bị ignore bởi luật ngoài fingerprint: `info/exclude`, excludes toàn cục, `.gitignore` untracked tự ignore chính nó (`ignored`, kèm file chứa luật). Không báo: file bị ignore bởi `.gitignore` nằm trong fingerprint (tracked, hoặc untracked mà không bị ignore), và entry sparse checkout bỏ khỏi đĩa. Gate xử lý theo §C.5 bước 0; store guard của hook từ chối submit khi `flagged` khác rỗng hoặc `hidden_files` lỗi (sau khi receipt đã khớp), không xét `ignored`.
- Chữ ký: `Signed { payload: String (JSON), hmac: hex }`, HMAC-SHA256 trên tag miền + đúng byte của `payload`; tag là `receipt\0` cho receipt và `approval\0` cho approval, nên chữ ký của loại này không kiểm được như loại kia. File ký kiểu cũ (không tag) bị từ chối (fail-closed): chạy lại gate / duyệt lại.
- Receipt hợp lệ để submit store: hmac đúng, `repo_root` trong receipt là đường dẫn canonical của chính repo đang kiểm (`check_store_receipt_in`), `tree_fp` khớp cây hiện tại, `mode == Release`, `status == Clear`, `store_compliance.status == Clear`; thêm ở hook: không có file tracked nào mang cờ index (bullet trên).
- Giới hạn trung thực (ghi vào SECURITY.md): chưa có sandbox thì agent cùng user đọc được key; đây là chống giả mạo vô ý. Từ P2, Seatbelt cấm agent đọc `AAF_DATA_DIR`.

### C.3 Hook (`aaf-hook`)

- Stdin: JSON PreToolUse của Claude Code (`tool_name`, `tool_input`, `cwd`, …). `Bash` đọc `tool_input.command`; `Write|Edit|MultiEdit|Read` đọc `tool_input.file_path`. P1 chỉ hỗ trợ Claude Code; agent khác là adapter sau.
- ALLOW: stdout `{}`, exit 0. DENY: stdout JSON `hookSpecificOutput.permissionDecision="deny"` + cùng lý do ra stderr, exit 2. Lý do: `<rule>: <reason> — fix: <action>`.
- Stdin không phải JSON ⇒ exit 2. JSON hợp lệ nhưng tool lạ ⇒ allow. Panic ⇒ exit 2. Không bao giờ thoát mã khác 0/2.
- `git_guard` deny: `push --force|-f|+refspec`; `--force-with-lease` vào nhánh bảo vệ (`main`, `master`, `release/*`); xoá nhánh bảo vệ (`branch -D`, `push --delete`, `push origin :main`, `update-ref -d`); `reset --hard`; `commit|push|merge --no-verify` và `commit -n`; `-c core.hooksPath=` / `config core.hooksPath`. Nhánh bảo vệ (`git_guard.rs` `is_protected`): `main`, `master`, `release/*` không phân biệt hoa thường ASCII, và mọi tên có ký tự không phải ASCII (APFS gộp `maﬆer`, `MAſTER` về ref của `master`).
- `git config` (`git_persist.rs` `config_args`, dùng chung cho `git_persist`, `git_guard` ~572 và `git_alias` ~184): giá trị của `--comment`, `--type`, `--default`, `--value`, `-f`/`--file`, `--blob` (kể cả viết tắt, trừ dạng `--opt=giá trị`) bị bỏ qua, không đọc như cờ đọc, verb hay key.
- Gộp tên như APFS (`paths::fold`, `paths.rs`): thành phần đường dẫn của file điều khiển git và tên file bảo vệ của `delete_guard` được so sau khi bỏ hoa thường ASCII và thay `ſ`, dấu Kelvin, `ß`/`ẞ`, chữ ghép `ﬀ`…`ﬆ` bằng chữ ASCII tương ứng.
- Alias git (`git_alias`): giá trị alias được xét như lệnh mà nó mở rộng thành. Alias định nghĩa trên dòng lệnh (`-c alias.x=…`) hay lưu bằng `git config alias.x …` mà phần mở rộng bị chặn thì bị chặn ngay lúc đó. Subcommand không phải lệnh dựng sẵn của git thì hook tra `alias.<tên>` trong cấu hình đã lưu (`git config --list -z`) và xét phần mở rộng (`git fp` với `alias.fp = push --force` bị chặn); không tra được thì từ chối.
- File điều khiển của git (`git_files`, rule `git_guard`): `config`, `config.worktree` của một git dir (của repo, của worktree liên kết dưới `worktrees/<tên>/`, của submodule dưới `modules/`), mọi thứ trong thư mục `hooks`, chính git dir và `worktrees/<tên>`, `modules/<tên>`, `refs/heads/<nhánh bảo vệ>`, `packed-refs`, `~/.gitconfig`, `~/.config/git/config`, `/etc/gitconfig`. Deny `Write|Edit|MultiEdit` vào đó; deny Bash redirect `>` vào đó; deny mọi chương trình không thuộc danh sách chỉ đọc (`READERS`: `cat`, `ls`, `grep`, `head`, `diff`, …; `find` không có hành động ghi/chạy; `sed`/`perl` không sửa tại chỗ; shell) khi một đối số, giá trị tuỳ chọn hay thư mục làm việc của nó là một trong các file đó (với `cp|install|rsync|ditto|scp` nguồn chỉ tính khi là cả git dir). Đọc thì được. Xét theo đường dẫn như viết và theo file mà symlink dẫn tới.
- Trạng thái git mà lệnh sau tin (`git_persist`, rule `git_guard`): deny `init|clone --template`, `GIT_TEMPLATE_DIR`, `init.templateDir`; `git config` lưu key mà git chạy như chương trình (giá trị boolean, đọc, unset được qua), `config --edit`, `rename-section`; remote `ext::`; dời nhánh bảo vệ bằng `update-ref`, `branch -f/-m/-c`, `checkout -B`, `switch -C`, `worktree add -B`, `symbolic-ref`, refspec fetch/pull từ nguồn khác hay tới remote là thư mục; `HOME`/`XDG_CONFIG_HOME` đặt ở lệnh trước trên cùng dòng.
- Phân tích shell: tokenizer có quote, tách `; && || |`, đệ quy vào `$(…)`, backtick, `sh|bash|zsh -c`, `eval`; bỏ qua tiền tố `VAR=x`, `command`, `env`, đường dẫn tuyệt đối tới git; hiểu `git -C <p>` và `git -c k=v`. Không parse được mà có token `git` kèm từ nguy hiểm ⇒ deny.
  - `env -S '<chuỗi>'` được tách thành `env <chuỗi>` (`shell/command.rs` ~319): `-i`, `-u TÊN`, `-P dir` ở đầu chuỗi là tuỳ chọn của `env`. Wrapper xoá môi trường đã gỡ trước đó (`env -i`, `env -`, `exec -c`, `sudo`, `doas`) phủ `env -S` đứng sau (~149).
  - Script của `sh|bash|zsh -c` là từ đầu tiên không phải tuỳ chọn (`shell_input` ~430); `-o/+o/-O/+O`, `--rcfile`, `--init-file` nhận giá trị; `-`, `--` kết thúc tuỳ chọn.
  - Shell đọc script từ stdin (`-s`, `-`, không có toán hạng): thân heredoc, here-string `<<<`, chuỗi `echo`/`printf` đưa qua pipe được tách dưới wrapper của shell (`stdin_scripts` ~471; thân heredoc mang trạng thái môi trường bị xoá của lệnh đọc nó, `shell.rs` ~566). Stdin không nằm trên dòng lệnh (`cat x | sh`, `sh < x`, `{ echo …; } | sh`) không được thấy, như `bash build.sh`. Hệ quả chặn thừa: heredoc đưa vào chương trình dưới `sudo`/`env -i` (trừ `cat` đứng một mình với delimiter có nháy) có dòng `aaf …` bị deny.
- `adb_guard`: file `.adb-denylist`, `.adb-allowlist` ở repo root và `~/.config/autofactory/`. Deny: serial trong denylist; có allowlist mà serial không thuộc; denylist không rỗng mà lệnh thiếu `-s` (và không có `ANDROID_SERIAL=` ngay trong lệnh). Deny lệnh phá máy: `fastboot flash|erase|oem unlock|flashing unlock`, `adb reboot bootloader|recovery`, `adb shell` chứa `rm -rf /`, `wipe`, `dd `, `mkfs`, `reboot -p`.
- `delete_guard` (chỉ trong repo root): mẫu bảo vệ `.env`, `.env.*`, `*.keystore`, `*.jks`, `*.p12`, `*.mobileprovision`, `google-services.json`, `GoogleService-Info.plist`, `.autofactory/config.toml`, `.claude/settings.json`, `.claude/settings.local.json`. Deny Bash `rm`, `unlink`, `git rm`, `mv <bảo vệ> …`, `truncate`, redirect `>` vào file bảo vệ, `git clean` có `-x|-X`. Deny `Write|Edit|MultiEdit` vào file bảo vệ.
- Bảo vệ data dir: deny `Write|Edit|MultiEdit|Read` vào `AAF_DATA_DIR`; deny Bash nhắc tới data dir (đường dẫn thật, `~/.local/share/autofactory`, `$AAF_DATA_DIR`, `receipt.key`) trừ khi lệnh đầu là `aaf` trần và dòng lệnh không định nghĩa lại `aaf` (hàm, `alias`, `hash`, `autoload`) hay đặt `PATH`.
- `store_submit_guard`: khớp `fastlane deliver|supply|pilot|upload_to_*`, `eas submit`, `xcrun altool --upload-app|--upload-package`, `gradlew publish*|promoteArtifact`. Khi khớp: kiểm receipt theo §C.2, sai ⇒ deny, fix: `aaf gate --release`. Git gọi có timeout 10 s; quá hạn ⇒ deny.
- `human_action_guard`: deny Bash chạy `aaf approve`, `aaf board unblock`, `aaf board unfreeze` (mọi đường dẫn tới `aaf`, qua wrapper, shell lồng hay `cargo run … -- …`; từ lệnh hoặc subcommand dựng lúc chạy cũng tính; qua `script`, `expect`, `unbuffer`, `socat`, `zpty`, `tmux`, `screen`, `ssh`, `osascript`): đây là việc của người, agent không tự duyệt. Cũng deny mọi thay đổi `AAF_RUN_ID` và `aaf` dưới `env -i`, `exec -c`, `sudo`, `doas`.
- `heavy_cmd_guard`: deny `gradle`/`gradlew`, `xcodebuild` và Unity batch (`-batchmode|-runTests|-executeMethod`) chạy trần; chỉ cho qua khi nằm trong `aaf slot [opts] -- <cmd>` (bắt buộc có `--`) hoặc đi qua `aaf gate`. Wrapper chỉ được công nhận khi từ lệnh đúng là tên trần `aaf` và dòng lệnh không định nghĩa lại `aaf` hay đặt `PATH` (ngoài payload): `./aaf`, `/tmp/x/aaf`, từ lệnh dựng lúc chạy hay `aaf` trên dòng như vậy thì payload bị xét như lệnh chạy trần. Deny mọi Bash tự gán `AAF_HEAVY_SLOT` với bất kỳ giá trị nào (tiền tố gán, `export`/`declare`/`typeset`/`readonly`/`local`, `env`, `sudo`, `read`/`printf -v`/`for`, đối số dạng `AAF_HEAVY_SLOT=…` của lệnh bất kỳ, kể cả trong shell lồng, `$(…)`, `env -S`): biến này chỉ do `aaf slot` đặt; `export` biến có tên dựng lúc chạy đứng cùng dòng với `aaf slot` cũng bị deny, còn đọc biến hay `unset` thì được. Lệnh nhẹ được phép: gradle chỉ gồm `--version -v --status --stop --help -h -?` (`help`, `tasks`, `projects`, `properties` vẫn chạy pha cấu hình và dựng daemon nên là lệnh nặng); xcodebuild có một trong `-version|-showsdks|-list|-help|-showBuildSettings` và mọi từ còn lại là selector kèm giá trị (`-project`, `-workspace`, `-scheme`, `-target`, `-configuration`, `-sdk`, `-arch`, `-destination`), `-json|-quiet|-verbose` hoặc `KEY=value`; Unity không có cờ batch. Payload sau `aaf slot --` chỉ được miễn guard này, mọi guard khác vẫn xét. Fix: `aaf slot -- <command> (aaf gate is run by the factory or the operator, not by an agent)`. Bảng lệnh nặng phải khớp bộ phân loại của engine (§C.11).
- Hiệu năng: quyết định fast-path trong tiến trình < 1 ms (assert trong test); wall-clock cả spawn in ra ở benchmark, không assert.
- Đăng ký là điều kiện để chạy agent: với executor `claude`, factory đọc `.claude/settings.json` TRONG worktree của task trước mỗi lần khởi động agent (lượt task, cross-audit, đề xuất subtask) bằng cùng code mà `aaf init` và `aaf doctor` dùng (`aaf_engine::hook_settings`): phải có một entry `hooks.PreToolUse` chạy chương trình tên `aaf-hook` với matcher phủ đủ `Bash`, `Write`, `Edit`, `MultiEdit`, `Read` (matcher rỗng hoặc `*` cũng tính). Thiếu file, JSON hỏng, không có entry hay matcher hẹp ⇒ không agent nào được khởi động, task sang `Blocked(NeedsHuman)` với lý do nêu cách sửa (commit `.claude/settings.json` trên nhánh base rồi `aaf board unblock`), không ghi run nào. Worktree chưa có run nào và thiếu đăng ký thì được rebase lên base trước khi kết luận, nên commit file xong là task chạy được. Executor khác (`codex`, `antigravity`, `opencode`, `custom`) không có hook nên không bị kiểm. Chỉ kiểm việc đăng ký: binary `aaf-hook` có chạy được hay không là việc của `aaf doctor`.
- Entry `aaf-hook` (`hook_settings/validate.rs`): chỉ `type: "command"`, `command`, và `timeout` là số nguyên ≥ 30 giây (`MIN_HOOK_TIMEOUT_SECS`) hoặc không có; `timeout` nhỏ hơn bị từ chối. `env` trong settings không được đặt `GIT_*` nào trừ `GIT_AUTHOR_*`/`GIT_COMMITTER_*`, cũng không `HOME`, `XDG_CONFIG_HOME`, `SSH_ASKPASS`, `BASH_ENV`, `ENV`, `ZDOTDIR`, `AAF_*`, `DYLD_*`, `LD_*` (`is_guard_env`). Kiểm trên base trước khi lấy task (`hook_settings.rs` `check_base` ~512): có `.claude/settings.local.json` hay không được hỏi bằng `git ls-tree --name-only <base> -- …` (rỗng = không có); git lỗi ở bước này, hay file có mà `git show` thất bại ⇒ `aaf run` từ chối, không task nào bị đụng.
- Đây là hàng rào, không phải biên an ninh: biên thật là sandbox và branch protection phía server (ghi vào SECURITY.md).

### C.4 Cấu hình 3 tầng (`aaf-engine::config`)

Tầng 1 `~/.config/autofactory/config.toml` < tầng 2 `.autofactory/config.toml` (commit) < tầng 3 `.autofactory/config.local.toml` < env `AAF_*` < cờ CLI.

Với `store_compliance = auto`, việc có áp dụng hay không do nội dung repo quyết định (§C.6), không theo `project.profile`.

Phát hiện Flutter ở `detect.rs` là bảo thủ: chỉ điền `flutter test` khi `pubspec.yaml` có `sdk: flutter` VÀ có thư mục `test/`.

- Type và mặc định: `aaf_domain::config`. Profile `auto` tự dò stack (`detect.rs`).
- Dò stack cho `aaf init`, hai trường hợp ngoài marker ở gốc repo: (1) Unity (`detect_unity.rs`): đọc `m_EditorVersion` trong `ProjectSettings/ProjectVersion.txt` và tìm assembly test EditMode đầu tiên dưới `Assets/` (asmdef chỉ cho platform `Editor` và tham chiếu test framework); có cả hai thì `test_scoped`/`test_full` là lệnh `-runTests` EditMode của đúng phiên bản editor đó ở vị trí Unity Hub trên macOS (`UNITY_PATH` chỉ binary khác), kết quả và log nằm ngoài project, file kết quả không có `<test-case` hoặc có case hỏng là thất bại; thiếu một trong hai thì lệnh để trống. ### C.5 Gate (`aaf-engine::gate`)

Chữ ký cố định: `gate::run_gate(repo_root: &Path, cfg: &RepoConfig, mode: GateMode, clock: &dyn Clock) -> Result<Receipt, GateError>`.
0. File mà fingerprint không thấy (`gate/hidden.rs`, §C.2), xét trước mọi thứ khác (trước cả `tree_fp` và luật dùng lại receipt): file tracked mang cờ index ⇒ `Blocked` ở mọi mode và mọi chính sách. File chỉ bị ignore bởi luật ngoài fingerprint theo `HiddenPolicy`: `Warn` (mặc định, `aaf gate` của người) ⇒ dòng `warning: work tree: …` trong `reasons`, status không đổi; riêng mode `Release` ⇒ `Blocked`, xét lại sau khi lệnh chạy; `Remove` (`run_gate_strict`, chỉ cho cây dưới `AAF_WORKTREE_DIR`, factory dùng qua `RealGate`) ⇒ xoá trước khi lệnh chạy và sau khi lệnh chạy, không xoá được hay còn sót ⇒ `Blocked`. Còn lý do chặn nào ở bước này thì không dùng lại receipt cũ. File bị ignore bởi `.gitignore` nằm trong fingerprint: không báo, không xoá, không ký, ở mọi mode.
1. Base: `gate.base_ref` (`auto` = `origin/HEAD` → `origin/main` → `origin/master` → `main` → `master`); lấy merge-base với HEAD; không có ⇒ HEAD.
2. Tập thay đổi: `git diff --name-status -M <base>` (cả phần chưa commit) + file untracked (tính là Added).
3. `static_checks` trên dòng thêm mới: `SEC-001` secret (private key header, `AKIA…`, `ghp_`, `github_pat_`, `sk-ant-`, `xox[bp]-`, `AIza…`) Critical; `SEC-002` gán mật khẩu/token dạng chuỗi Warn; `LAZY-001` placeholder (`// ... existing code ...`, `todo!()`, `unimplemented!()`, `TODO: implement`, `NotImplementedError`) Critical; `ERR-001` nuốt lỗi (catch rỗng, `except: pass`) Critical; `LOG-001` log thô (`console.log`, `System.out.println`, `printStackTrace`, `dbg!`) Warn, bỏ qua file test. Bỏ qua binary, lockfile, thư mục sinh. Miễn trừ inline `aaf:allow(RULE) lý do`, đếm vào `suppressions` của receipt.
4. `head_lock`: file khớp `gate.head_lock_globs` có trạng thái M/D/R; file Added (kể cả untracked) được miễn, trừ file khớp `AGENT_CONFIG_GLOBS` (`gate/head_lock.rs`, `locked_path`). `lock_fp` = sha256 của danh sách đã sắp xếp (đường dẫn, trạng thái, blob hash). Có approval ký hợp lệ cho `lock_fp` ⇒ `Approved`, không ⇒ `Blocked`.
5. `store_compliance::scan` (§C.6).
6. `runner`: Scoped = lint + test_scoped; Full và Release = lint + build + test_full. Lệnh test của mode rỗng ⇒ `Unverified`. Chạy `sh -c` ở repo root, process group riêng, timeout `gate.command_timeout_secs`, giữ 4 KB cuối log. Khác 0 ⇒ `Blocked`.
7. Tính `tree_fp` trước và sau khi chạy lệnh; khác nhau ⇒ `Unverified` ("tree changed during gate").
8. Ký và ghi receipt. Trạng thái: `Clear` (exit 0), `Blocked`/`Unverified` (exit 2), lỗi runtime (exit 1).

### C.6 Store compliance (`aaf-engine::store_compliance`)

Chữ ký cố định: `store_compliance::scan(repo_root: &Path, cfg: &RepoConfig, release: bool) -> StoreComplianceReport`.
Kích hoạt: `off` ⇒ `Skipped`; không dò thấy Android/iOS/Flutter/RN/Expo ⇒ `NotApplicable`. Loại trừ `build/`, `.gradle/`, `node_modules/`, `Pods/`, `Carthage/`, `.build/`, `DerivedData/`.

CRITICAL (parse tất định; không phân giải được thì vào `unresolved` + WARN):
- `AND-001` `android:debuggable="true"` ở manifest `src/main` hoặc `src/release`.
- `AND-002` component có `<intent-filter>` thiếu `android:exported`.
- `AND-003` targetSdk < `gate.min_android_target_sdk` (mặc định 36). Phân giải: số literal trong `build.gradle(.kts)`, `gradle/libs.versions.toml`, `ext`/`gradle.properties`, Expo `app.json`. Flutter `flutter.targetSdkVersion` ⇒ unresolved.
- `IOS-001` `NS*UsageDescription` rỗng hoặc placeholder: nguồn `Info.plist`, `INFOPLIST_KEY_*` trong `project.pbxproj`, Expo `expo.ios.infoPlist`. Placeholder = cả giá trị (không phân biệt hoa thường) thuộc {todo, tbd, test, placeholder, description, xxx, ...} hoặc bắt đầu bằng `TODO`/`TBD`/`FIXME`/`Lorem ipsum`. `$(VAR)` và `app.config.js|ts` ⇒ unresolved.
- `IOS-002` mã nguồn app (Swift/ObjC) dùng Required Reason API (`UserDefaults`, `NSUserDefaults`, `fileModificationDate`, `contentModificationDateKey`, `creationDateKey`, `systemUptime`, `mach_absolute_time`, `volumeAvailableCapacity`, `systemFreeSize`, `activeInputModes`) mà không có `PrivacyInfo.xcprivacy`.
- Kotlin Multiplatform (`kmp.rs`) cũng tính vào `IOS-002`/`IOS-101`: file `.kt` dưới `src/<source set Apple>/` (`iosMain`, `appleMain`, `iosArm64Main`, `iosX64Main`, `iosSimulatorArm64Main`; source set test không tính) dùng Required Reason API qua `platform.*`. Một symbol chỉ tính khi file import nó từ `platform.*` (theo tên hoặc wildcard của package) hoặc viết tên đầy đủ; hàm C của `platform.posix`/`platform.darwin` (`stat`, `fstat`, `lstat`, `fstatat`, `statfs`, `statvfs`, `fstatfs`, `fstatvfs`, `getattrlistbulk`, `mach_absolute_time`) chỉ tính khi là lời gọi. Danh sách theo trang NSPrivacyAccessedAPIType của Apple (đọc 22/11/2026); `getattrlist`, `fgetattrlist`, `getattrlistat` bị bỏ ra vì thuộc hai category tuỳ thuộc tính được hỏi. Comment được bỏ trước khi dò.

WARN: `AND-101` `usesCleartextTraffic="true"` thiếu `networkSecurityConfig`; `AND-102` quyền nhạy cảm (`READ_SMS`, `READ_CALL_LOG`, `MANAGE_EXTERNAL_STORAGE`, `REQUEST_INSTALL_PACKAGES`, `QUERY_ALL_PACKAGES`, `ACCESS_BACKGROUND_LOCATION`); `AND-103` `allowBackup="true"`; `IOS-101` có `PrivacyInfo.xcprivacy` nhưng thiếu category khớp API đang dùng; `IOS-102` usage description ngắn hơn 10 ký tự.
Status: có Critical ⇒ `Blocked`, ngược lại `Clear`.

### C.7 SQLite (`aaf-engine::db`)

Một thread ghi duy nhất mỗi tiến trình (actor qua `std::sync::mpsc`); giữa các tiến trình dựa vào `busy_timeout=5000` + `BEGIN IMMEDIATE`. `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`.
Bảng: `tasks`, `root_budgets`, `task_deps`, `runs`, `accounts(id, provider, config_dir, cooldown_until, name)`, `events` (append-only), `closed_fingerprints`, `meta(key, value)`. Token 5h/7d suy ra từ `runs`, không lưu cột riêng.
`Db` implement mọi trait trong `aaf_domain::ports`: `TaskStore`, `BudgetStore`, `RunStore`, `AccountStore`, `EventSink`, `FingerprintStore`, `KvStore`. `add_dep` gọi `aaf_domain::dag` và từ chối vòng. Migration có version, chạy lại an toàn, có test nâng từ schema cũ. Cột `accounts.name` (tên hiển thị) thêm ở migration version 3; dòng cũ có `name` rỗng thì đọc ra tên mặc định suy từ `config_dir` cho tới lần discovery kế tiếp ghi tên thật.

### C.8 Accounts, executors, git

- `accounts/discovery`: quét `discovery_globs` tìm config dir Claude Code; dò thêm Codex (`~/.codex`), Antigravity/Gemini (`~/.gemini`), OpenCode (`~/.config/opencode`) khi có binary trên PATH. Không đọc Keychain, không đọc file credential, không symlink.
- Tên hiển thị (`AccountProfile.name`, lộ ra ở `AccountView.name`): mặc định là thành phần cuối của config dir, bỏ tiền tố `.claude-` hoặc `.` (`~/.claude-work` ⇒ `work`, `~/.codex` ⇒ `codex`). `accounts.aliases` (tầng 1; key = đường dẫn config dir, cho phép `~`; value = tên) ghi đè khi đường dẫn canonical trùng. Id không đổi theo tên.
- `accounts/lease`: `File::try_lock` trên `leases/<account_id>.lock`, giữ suốt run, tự nhả khi tiến trình chết.
- `accounts/router`: chọn account không cooldown, lease rảnh, ít token nhất trong 5 giờ (`next`), hoặc cũng luật đó trong số account mà bộ lọc của người gọi chấp nhận (`next_where`). `LimitHit` ⇒ cooldown tới `reset_at`, không có thì `now + 5h`.

### C.9 Unblocker, detector, cross-audit

- Thang: T1 phân loại tất định (`classifier`) → T2 xử lý cơ học (quota: cooldown, rồi đổi account hoặc chờ theo câu trả lời của pool: `pinned` luôn chờ, `sticky`/`least_used` đổi khi còn account chưa cooldown và chờ khi hết; chỉ khi không có pool trả lời, thang mới đoán theo số lần lặp như trước, lần đầu đổi, lần hai chờ; flaky: chạy lại 2/2; conflict: rebase + gate lại) → T3 chạy lại task với context mới + tóm tắt lỗi thêm vào `context_notes` (spec bất biến) → T4 tách subtask ở depth 1, dùng chung root budget → T5 chuyển `Blocked(NeedsHuman)` + webhook.
- Root budget: token = input + output + cache_creation; vượt token, wall-clock hoặc số vòng ⇒ đóng băng root. `global_freeze_consecutive_fails` root thất bại liên tiếp ⇒ đóng băng cả factory (`meta.factory_frozen`) tới khi `aaf board unfreeze`.
- `detector/fingerprint`: chuẩn hoá stack trace (bỏ số dòng, PID, địa chỉ, UUID, timestamp) rồi sha256; trùng fingerprint đã đóng trong 72 giờ ⇒ không tạo task mới, gắn vào task cũ.
- `detector/repro`: hàm thư viện `verify` (thất bại 2/2 lần liên tiếp mới tính là tái hiện được) dùng `ReproCommand::argv` chạy thủ công; không lệnh CLI hay bước nào của factory tự thực thi `commands.repro`.
- `detector/github_issues` & `aaf board import-issues [--label <L>] [--dry-run]`: gọi `gh` đã phân giải ngoài repo qua `aaf_fp::tools` (`aaf_fp::program("gh")`); chỉ nhận issue và comment của tác giả trong `owner_github_allowlist` (rỗng = fail-closed, không tin ai); nội dung bọc khung `<<<UNTRUSTED_DATA_BEGIN id=…>>>` / `<<<UNTRUSTED_DATA_END id=…>>>` kèm id băm nội dung trước khi vào prompt/spec (trong khi `aaf plan` dùng thẻ `<untrusted-data id="…">`); khử trùng theo task mở và cửa sổ 72 giờ. `aaf board sync-github` dùng `gh project view|field-list|item-list|item-add|item-edit` (Projects v2) hoặc `gh issue view|edit` (nhãn `status:*`), giữ một task thẩm quyền duy nhất cho mỗi issue và trả exit 2 (`partial_error`) khi có mục lỗi.
- `cross_audit` & `[cross_audit]`: checklist nhị phân (có `cfg!(test)`/nhánh chỉ-test trong code sản phẩm, giá trị hardcode để qua test, lộ secret, lệch acceptance criteria, sửa/xoá assertion) chạy qua `AgentRunner` trong worktree sạch của `base`, bọc Seatbelt sandbox + env allow-list; verdict PASS mới phát approval ký cho `lock_fp`; ghi `same_account` khi cùng account. Hỗ trợ `[cross_audit]` ở cả tầng 1 (`GlobalConfig`) và tầng 2 (`RepoConfig`: trường không rỗng ở tầng 2 ghi đè tầng 1, `require_different_provider` lấy OR; tầng 3 chỉ siết được `require_different_provider = true`); khi `require_different_provider = true` mà không có provider khác hợp lệ thì fail-closed (không tự ký approval). Ở `pinned` cùng provider, `same_account = true` là trạng thái bình thường.

### C.10 CLI (`aaf`)

`init` · `doctor` · `accounts list|next|cooldown` · `gate [--scoped|--full|--release]` · `approve --reviewer <name>` (đòi TTY, từ chối khi có `AAF_RUN_ID`) · `board add|list|show|unblock|unfreeze|rework|split|trace|import-issues|sync-github` · `run [--auto] [--auto-merge] [--auto-split] [--max-parallel N|auto] [--unsandboxed]` · `slot [--label <tên>] [--timeout <giây>] -- <lệnh> [tham số…]` · `status [--all]` · `watch [--repo <path>|--all] [--interval <giây>] [--once]` · `plan` · `proof` · `skills`.
`--json`: stdout đúng một JSON object `{ok, command, status, …, duration_ms}`. Exit: 0 thành công/Clear, 1 lỗi runtime/config/I/O, 2 Blocked/Unverified/vi phạm policy.
`run`: JSON mang các trường của `RunSummary` (`agent_runs`, `gate_runs`, `done`, `review`, `blocked`, `requeued`, `waiting_for_account`, `frozen`, `halted`, `errors`), `warnings` của config, `max_parallel` hiệu dụng và `auto_split_count`. `--max-parallel auto` tự tính trần song song (1..=4) từ số account, `max_concurrent_per_account`, số CPU và áp lực bộ nhớ hiện tại (`aaf_engine::split::compute_auto_parallel`; `0` bị từ chối exit 2). `--auto-split` chạy trước vòng factory một lượt planner chỉ đọc trên các task gốc `Ready` chưa có subtask/ghi chú `split:` để phân rã thành 2..=4 subtask có `owned_paths` rời nhau và nối DAG (`aaf board split <id> [--max 2..=4] [--dry-run] [--unsandboxed]` là lệnh thủ công tương ứng, từ chối trong `AAF_RUN_ID` và với subtask hoặc task không ở `Ready`/`Backlog`). Exit 2 với `ok: false` khi: factory đóng băng (`status: "frozen"`), lượt chạy dừng vì agent CLI lỗi đăng nhập hay mạng (`status: "halted"`, `halted` nêu task, lỗi và cách sửa; task đó ở `Ready`, §C.8), hoặc có ít nhất một task kết thúc lượt này ở `Blocked` (`status: "blocked"`; mọi lỗi hạ tầng chặn task, trừ lỗi đăng nhập/mạng của agent ở trên, đều đưa task đó vào `blocked`). Exit 0 / `status: "ok"` khi không task nào bị chặn, kể cả lúc `errors` có dòng không chặn gì: không mở được pull request (task vẫn ở `Review`), không fetch được base, không dọn được worktree của task đã xong. `agent_runs` đếm job agent đã được giao, kể cả job bị chặn trước khi agent khởi động.
`gate`: JSON có `reused_receipt` (bool): `true` khi kết quả là receipt `Clear` đã lưu được trả lại theo luật dùng lại của §C.11 và không lệnh nào chạy ở lượt này; bản in cho người thêm dòng `reused receipt: …`.
`slot`: chạy một lệnh bất kỳ qua đúng hàng chờ lệnh nặng của gate (§C.11); dành cho git hook, CI và agent (không từ chối khi có `AAF_RUN_ID`), chạy được ngoài repo git. Lệnh PHẢI đứng sau `--`; thiếu `--` là lỗi cú pháp (exit 2, không chạy gì). stdout/stderr của lệnh là của bên gọi (không bắt lại), `aaf` chỉ in tiến độ chờ ra stderr. Exit = exit của lệnh (bị giết bởi tín hiệu ⇒ 128 + số tín hiệu); hết `--timeout` khi còn CHỜ khe ⇒ 75 và lệnh không được chạy; không khởi động được lệnh ⇒ 127 (không thấy) hoặc 126; `--json` bị từ chối (exit 2) vì stdout thuộc về lệnh. Không có `--timeout` ⇒ chờ như gate. Nhãn mặc định = từ đầu tiên của lệnh; khoá thống kê = id thống kê của repo khi ở trong repo, ngoài repo = hash của cwd.
`doctor`: mỗi mục có `name`, `ok`, `required`, `applicable`, `detail`; exit 2 khi một mục `required` không `ok`. Ngoài repo git, `aaf doctor` là doctor của máy: bốn mục của repo (`repo_root`, `hook_registered`, `hook_binary`, `hook_committed`) có `applicable: false`, in `n/a` và không quyết định gì. Trong repo: `hook_registered` (bắt buộc) dùng cùng luật với factory (§C.3) trên file ở working tree; `hook_binary` (bắt buộc) kiểm chương trình mà entry trỏ tới có chạy được; `hook_committed` (cảnh báo) so `.claude/settings.json` với HEAD qua `git status --porcelain --ignored`: untracked, bị ignore, khác HEAD hay không so được thì cảnh báo, vì worktree của task được cắt từ commit.
`accounts next` và `doctor` cho thấy chế độ và việc gắn (trường JSON thêm vào, không đổi trường cũ): `accounts next` có `selection` và `binding` (`account`, `source` = `settings` | `history` | `first_use`, `cooldown_until`, `settings_account`, `settings_account_known`); ở `pinned`, khi account đã gắn đang cooldown hoặc bị lease thì `account` là `null` và exit 2 dù account khác còn rảnh. JSON của `doctor` có object `accounts` với `selection`, `binding`, `settings_account`. JSON của `run` có `account_binding`.
`doctor` (mục chỉ cảnh báo, không đổi exit): `keychain_sandbox_exposure` (macOS: cảnh báo Seatbelt giữ `~/Library/Keychains` đọc được vì chặn sẽ làm hỏng `claude -p` OAuth, SECURITY.md §10 #3); `gradle_daemon` liệt kê Gradle/Kotlin daemon đang sống kèm RSS; `gradle_daemon_config` cảnh báo khi lệnh nặng của repo gọi Gradle thiếu `--no-daemon` mà `gradle.properties` không đặt `org.gradle.daemon=false`; `git_hooks_heavy` đọc `pre-commit`/`pre-push` trong thư mục hook hiệu lực (`core.hooksPath`, không có thì `hooks` của repo) và các script chúng gọi (một tầng, trong repo, ≤ 256 KB, chỉ text), cảnh báo `file:dòng` khi một lệnh gọi `gradle`/`gradlew`/`xcodebuild`/`Unity`/`unity-editor` mà không bọc `aaf slot --` hoặc `aaf gate`. Các dòng kết thúc bằng `\` được nối thành một lệnh trước khi xét và báo số dòng đầu: `aaf slot -- \` + `./gradlew …` ở dòng sau là đã xếp hàng; lệnh nối dòng mà không phần nào đi qua hàng chờ thì dòng nào tự nó là lệnh build vẫn bị báo.
`watch`: dashboard terminal 100% chỉ đọc (0 cổng mạng, chỉ dùng `try_lock_shared()` không lấy khoá độc quyền, mở DB WAL trên thư mục chỉ đọc bằng `mode=ro&immutable=1` khi không có `-wal` và kiểm `PRAGMA user_version <= SCHEMA_VERSION`, không ghi DB, không bao giờ tự tạo `receipt.key`, lọc chuỗi ANSI/OSC và xử lý `BrokenPipe` sạch), hiển thị 4 bảng trực tiếp: task theo 8 trạng thái + danh sách chưa kết thúc (`unblock_cycles`, `blocked_reason`), khe nặng (`drain_active`, `memory_pressure`, `measured_commands`, từng `heavy.<n>.lock` ở trạng thái `free`/`busy`/`orphan`/`stale`), pool account (`selection_mode`, `pinned_account`, cooldown, `tokens_5h`), và tóm tắt biên nhận ký gần nhất (`status`, `mode`, `tree_fp_short`, `warnings`, `created_at`). `--once` (và `--json`) in một snapshot rồi thoát 0 ngay không sleep; chế độ trực tiếp làm mới theo `--interval` (mặc định 2 s), nhấn `q` hoặc Ctrl-C để thoát sạch.
`init`: dò stack, sinh `.autofactory/config.toml`, gộp (không ghi đè) hook PreToolUse matcher `Bash|Write|Edit|MultiEdit|Read` vào `.claude/settings.json`, thêm `.autofactory/config.local.toml` vào `.gitignore`; từ chối (exit 2) khi có `AAF_RUN_ID`. Hook có trên `PATH` thì được đăng ký bằng tên trần `aaf-hook` (dạng đi được sang máy khác và vào worktree của task); chỉ có cạnh binary `aaf` thì đăng ký bằng đường dẫn tuyệt đối đã quote cho shell. JSON, object `hook`: `settings_path`, `action` (`added|updated|unchanged`), `matcher`, `command`, `binary`, `source` (`path|sibling`), `registered_as` (`name|absolute_path`), `tracking` (`committed|modified|untracked|ignored|unknown`, trạng thái của file trong git sau khi ghi), `commit_required` (`true` khi `tracking` khác `committed`). Khi cần commit, bản in cho người nêu lệnh `git add .claude/settings.json .autofactory/config.toml .gitignore && git commit`.

### C.11 Chống quá tải máy (lệnh chủ repo 22/11: máy hay đứng; 10 task nhỏ không được chạy Gradle 10 lần; xếp hàng không được làm kẹt task)

Cấu hình: `[machine]` ở tầng 1 (`aaf_domain::config::MachineConfig`): `max_heavy_parallel` (0 = tự động), `max_load_percent` (150; 0 = tắt kiểm tải), `heavy_wait_secs` (1800), `low_priority` (true).
- Lệnh nặng = `commands.build`, `commands.test_scoped`, `commands.test_full` của gate, và mọi lệnh chạy qua `aaf slot -- <lệnh>` (§C.10). Kiểm tĩnh, head_lock, store scan là nhẹ: chạy ngay, không cần khe, để lỗi rẻ lộ trước khi xếp hàng. `commands.lint` được xếp theo NỘI DUNG lệnh, không theo tên key: bộ phân loại lệnh độc quyền bên dưới nhận ra công cụ build trong chuỗi lệnh (`./gradlew lint`, `xcodebuild …`) thì lint đi qua hàng chờ như lệnh nặng; lint khác (`cargo clippy`, `eslint`…) chạy ngay.
- Khe toàn máy (`aaf-engine::throttle`): `File::try_lock` trên `throttle/heavy.<n>.lock` trong `AAF_DATA_DIR`, `n <` trần; dùng chung cho mọi repo và mọi tiến trình `aaf` (gate, factory, `aaf slot`). Trần = `max_heavy_parallel`, 0 thì bằng số CPU / 4 (ít nhất 1). Tiến trình giữ khe chết thì kernel tự nhả. Chờ khe không có trần thời gian (người giữ bị chặn bởi `gate.command_timeout_secs`), trừ `aaf slot --timeout`. `ponytail: thăm dò try_lock có backoff + jitter, nâng lên hàng đợi có vé khi > 8 tiến trình chờ`.
- Nhận lệnh theo RAM đã học: mỗi lệnh nặng chạy xong ghi RAM đỉnh của process group (lấy mẫu `ps -o rss=` theo chu kỳ của watchdog) và thời lượng vào `heavy_stats.json` trong `AAF_DATA_DIR`, khoá = (`repo_id`, nhãn lệnh), giữ giá trị lớn nhất của 5 lần gần nhất. Khe ≥ 1 chỉ nhận khi lệnh đã có số đo VÀ RAM trống hiệu dụng ≥ 1,25 × đỉnh đã ghi; lệnh chưa từng đo chỉ chạy khi không khe nào khác bận và giữ mọi khe trong lúc chạy. File stats hỏng hay thiếu ⇒ coi như chưa đo (chạy một mình), không lỗi. Một lần đọc 0 byte không phải số đo (`throttle/watchdog.rs` ~378: tiến trình còn chạy luôn có trang thường trú, 0 byte là `ps` bắt được tiến trình đã thoát); lệnh xong trước khi có lần đọc khác 0 không ghi số đo nào, vẫn là "chưa từng đo" và lần sau vẫn chạy một mình.
- Giữ chỗ RAM: tiến trình giữ khe ghi vào nội dung file khoá `token=<32 hex>` (dòng đầu, xem "Lồng nhau"), `reserved=<1,25 × đỉnh đã ghi | unknown>` và, khi lệnh đã chạy, `pgid=<process group của lệnh>` cùng `lstart=<thời điểm bắt đầu của leader>` (nội dung chỉ có nghĩa khi đang có người giữ khoá; file quyền 0600, độ dài cố định khi đang giữ, bị xoá trắng khi nhả khe và khi người kế tiếp lấy khoá). RAM trống hiệu dụng = RAM trống − Σ trên các khe bận của max(0, `reserved` − RSS hiện tại của group đó); nhờ vậy hai lệnh 6 GB khởi động sát nhau trên máy trống 8 GB không cùng được nhận. Khe bận mà không đọc được giữ chỗ, hoặc `unknown` ⇒ không nhận thêm (không báo lỗi).
- `aaf` bị giết, lệnh còn chạy (`Busy::Orphaned`): lệnh nặng có process group riêng; khi `aaf` giữ khe bị giết cùng relay của nó (bullet "Relay tín hiệu" bên dưới), lệnh sống tiếp, còn kernel nhả khoá ngay. File khoá của khe vẫn còn `pgid=<group>` và dòng `lstart=<thời điểm bắt đầu của leader theo ps>` do người giữ ghi. Ai lấy được khoá của một file còn nội dung thì xét group đó trước: leader còn sống và `lstart` trùng, hoặc leader đã mất mà group còn thành viên ⇒ khe vẫn tính là bận (`Busy::Orphaned { pgid }`, tiến độ chờ in ra pgid), file giữ nguyên; không có `lstart` hay `lstart` lệch (pgid đã thuộc tiến trình khác) ⇒ khe được lấy và file bị xoá trắng. Không giết gì: khe trở lại khi lệnh kết thúc.
- Relay tín hiệu (`throttle/relay.rs`): một `/bin/sh` ở lại trong process group của `aaf`, chuyển INT/TERM/HUP mà terminal gửi cho group đó sang group của lệnh. Khi tín hiệu (TERM, INT, HUP, kể cả SIGKILL) chỉ gửi cho tiến trình `aaf`, relay không nhận nó nhưng pipe mà `aaf` giữ đóng lại mà chưa có dòng `done`: relay gửi TERM cho group của lệnh, chờ 10 giây (`GRACE_SECS`), rồi SIGKILL lặp có giới hạn tới khi `kill -0` thấy group rỗng. Chỉ làm vậy khi leader của group là con của `aaf` lúc relay khởi động (pgid bịa hay đã cấp lại không bị gửi gì). Lệnh chỉ sống tiếp sau `aaf` khi relay cũng chết (SIGKILL cả group của `aaf`, factory giết group của một gate); khi đó `Busy::Orphaned` ở trên giữ khe. Test: `aaf-cli/tests/cli_signal_alone.rs` (TERM, HUP cho `aaf slot`; TERM cho `aaf gate`).
- Lệnh độc quyền: lệnh gọi `gradle`/`gradlew`/`gradlew.bat`, `xcodebuild`, `Unity`/`unity-editor` (theo tên file của chương trình, không phân biệt hoa thường, ở vị trí bắt đầu lệnh, kể cả sau `sh -c`, `env`, `nice`, `&&`, `;`…) hoặc có tham số `-batchmode`/`-runTests`/`-executeMethod` LUÔN chạy một mình như lệnh chưa đo, bất kể `heavy_stats` nói gì; số đo vẫn được ghi nhưng không bao giờ dùng để nhận song song. Giá trị của tuỳ chọn có tham số của lệnh bọc được bỏ qua (`env -u VAR`, `sudo -u USER`, `nice -n N`, `timeout -s SIG`, `xargs -I X`, `arch -arch X`…; bảng khớp `wrapper_len` của `aaf-hook`). Với argv của `aaf slot`, mỗi phần tử là một từ nguyên vẹn (đường dẫn có dấu cách như `/tmp/my app/gradlew` vẫn là Gradle); chỉ script của shell `-c` mới được đọc như một dòng lệnh, và script đó là từ đầu tiên sau mọi tuỳ chọn của shell (`sh -c -- …`, `bash -c -x …`, `bash -c -o pipefail …`; `-o/+o/-O/+O`, `--rcfile`, `--init-file` nhận giá trị), không phải từ ngay sau `-c`. Tuỳ chọn của `arch` và `xcrun` là cả một từ, không tách thành cụm chữ cái (`arch -arm64e ./gradlew test` là Gradle); `-F` của `script` (macOS) là cờ không nhận giá trị (`throttle/heavy.rs`). Một bộ phân loại duy nhất (`throttle::heavy`) cho gate, `aaf slot` và `doctor`; bảng của nó phải là tập cha của bảng `heavy_cmd_guard` trong `aaf-hook` (hook cho qua lệnh chỉ hỏi thông tin như `gradle --version`; ở đây chúng vẫn độc quyền).
- Tắt daemon: mọi lệnh nặng được chạy với `GRADLE_OPTS` = giá trị sẵn có + `-Dorg.gradle.daemon=false` + `-Dorg.gradle.project.kotlin.compiler.execution.strategy=in-process` (không sửa chuỗi lệnh của người dùng), vì `GradleDaemon`/`KotlinCompileDaemon` chạy ở session khác: RSS không đo được và `SIGSTOP` không tới. Gradle vẫn có thể fork daemon dùng một lần khi `org.gradle.jvmargs` khác JVM client (tài liệu Gradle), nên tính độc quyền ở trên mới là lớp bảo vệ chính. Sau một lệnh Gradle, trước khi nhả khe: daemon mới xuất hiện trong lúc chạy và còn sống ⇒ ghi cảnh báo `throttle: gradle daemon still running pid=…; builds are not using --no-daemon` vào `reasons` (không giết, không đổi status).
- Chống đói lệnh chạy một mình: lệnh chưa đo/độc quyền chờ quá 60 giây (`ponytail: hằng số DRAIN_AFTER_SECS, đưa vào [machine] khi cần`) thì giữ `throttle/drain.lock`; khi khoá này có tiến trình sống giữ, lệnh đã đo không được nhận vào khe nào, các khe cạn dần và lệnh đang chờ tới lượt; nó nhả khoá khi có khe (chết thì kernel nhả).
- Lồng nhau: mỗi lần giữ khe sinh một token ngẫu nhiên 128 bit (32 hex, đọc từ `/dev/urandom`), ghi `token=<hex>` vào `locks/heavy.<n>.token` của mọi khe đang giữ (phần đóng của data dir; file khoá trong `throttle/` chỉ chứa giữ chỗ RAM, pgid và thời điểm bắt đầu); lệnh do throttle khởi chạy mang biến `AAF_HEAVY_SLOT=<khe>:<token>`. `aaf slot` chỉ chạy lệnh ngay, không xếp hàng (nếu không sẽ chờ chính tổ tiên của mình) khi biến có đúng dạng đó VÀ khe được nêu đang có người giữ VÀ file token của khe ấy chứa đúng token đó. Chỉ có số khe (`0`), `0:`, token thiếu/sai, hay token của một lượt đã kết thúc đều không được coi là "đang ở trong khe": lệnh xếp hàng như thường. Khe 0 cũng được xét (lệnh bị tạm dừng ở khe sau chuyển lên khe 0 và mang token theo) nhưng theo cùng luật: đang giữ và đúng token; khe 0 chỉ "đang bận" không mở được gì. Lệnh lồng vẫn nhận `GRADLE_OPTS` tắt daemon; ưu tiên thấp và watchdog không đặt lại vì nó thừa hưởng nice/taskpolicy và nằm trong process group mà watchdog của người giữ khe đang đo và tạm dừng. Token chỉ chặn tiến trình không đọc được file khoá/môi trường của người giữ; việc agent tự gán `AAF_HEAVY_SLOT` do `aaf-hook` chặn (§C.3).
- Trước khi chạy (đã có khe): áp lực bộ nhớ khác `Normal` ⇒ chờ tiếp, không trần. Tải 1 phút / số CPU vượt `max_load_percent` ⇒ chờ tối đa `heavy_wait_secs`, hết hạn vẫn chạy và ghi `degraded` (tải CPU không bao giờ làm kẹt task). Đo qua trait `LoadProbe` (macOS: `sysctl -n vm.loadavg`, `sysctl -n kern.memorystatus_vm_pressure_level`, `vm_stat`; Linux: `/proc/loadavg`, `/proc/pressure/memory`, `/proc/meminfo`); không đọc được ⇒ coi như bình thường kèm cảnh báo, riêng RAM trống không đọc được ⇒ không nhận ở khe ≥ 1. Thời gian qua `Clock` + trait ngủ, test không sleep thật.
- `low_priority`: lệnh nặng chạy qua `nice -n 10`, trên macOS thêm `taskpolicy -b` khi có binary; thiếu thì chạy thường.
- Đang chạy mà áp lực bộ nhớ lên `Critical`: `SIGSTOP` cả process group của lệnh vào khe muộn nhất (qua `/bin/kill`), về `Normal` thì `SIGCONT`; khe 0 không bao giờ bị dừng, nên luôn có một lệnh tiến. Thời gian bị dừng không tính vào timeout của lệnh. Không giết.
- Group bị dừng mà `aaf` chết: mỗi lần dừng ghi `locks/paused.<pgid>` (giữ khoá suốt lúc dừng) kèm `lstart=<thời điểm bắt đầu của leader theo ps>`. Lượt chạy nặng kế tiếp quét các bản ghi mất chủ: chỉ gửi `SIGCONT` khi group còn tiến trình, đang ở trạng thái dừng (`T`) và `lstart` của leader trùng bản ghi (leader đã mất nhưng thành viên còn dừng thì vẫn tiếp tục, vì pgid chưa thể bị cấp lại); ngược lại chỉ xoá bản ghi. Tránh gửi tín hiệu cho một pgid đã bị tái sử dụng. `ps` không trả lời (lỗi, hay quá `PROBE_TIMEOUT` 2 s, đã thấy khi tải 50–75) là `probe::Unreadable`, khác với "không có group": lượt quét (`throttle/orphans.rs` `resume_orphans` ~145) giữ nguyên bản ghi cho lượt sau, không xoá. Khi quá giờ, watchdog đọc lại cây ngay trước khi kill group (`Supervise::before_kill`) và `signal_verified` hỏi `ps` tối đa 3 lần (`SIGNAL_READS`); không có câu trả lời thì gửi theo pid các thành viên thấy lần cuối. Reaper hỏi `ps` tối đa 3 lần (`PS_READS`). Mọi trình chạy lệnh đọc đầu ra qua socket pair (`aaf-fp/src/output.rs`) vì đầu ghi của pipe có thể lọt sang tiến trình con của thread khác trên macOS.
- Log của lệnh: stdout và stderr đi chung MỘT pipe nên 4 KB cuối giữ đúng thứ tự lệnh đã ghi (hai pipe từng làm dòng tổng kết bị đẩy khỏi phần đuôi khi máy tải nặng).
- Dùng lại biên nhận: receipt đã ký `Clear`, cùng `repo_root` (canonical), cùng `tree_fp`, cùng `base_sha` (base được phân giải TRƯỚC khi xét dùng lại), cùng `config_hash`, mode đã chạy ≥ mode đang xin (`Scoped < Full < Release`) ⇒ trả lại receipt đó, không chạy lệnh nào. Base đã dịch chuyển ⇒ gate chạy lại, vì kiểm tĩnh và head_lock xét phần chênh so với base.
- `aaf slot` trong sandbox của agent (`throttle::paths`, `throttle::slot_file`): tiến trình không ghi được `throttle/` là "khách". Khách khoá chính các file khoá mà gate dùng (khoá được trên file chỉ-đọc), nên khách và gate loại trừ nhau bằng khoá của kernel. Người giữ ngoài sandbox ghi giữ chỗ RAM, pgid, thời điểm bắt đầu vào file khoá (khách đọc được, không ghi được) và token vào `locks/heavy.<n>.token` (khách không đọc được). Khách ghi cả token lẫn giữ chỗ của mình vào `throttle/guest/heavy.<n>.rec`. Bản ghi nào được đọc do file khoá quyết định: file khoá có nội dung thì người giữ là ngoài sandbox và file của khách không được xét. Bản ghi của khách không bao giờ được tin khi khe không có ai giữ khoá (không có "lệnh mồ côi" của khách: `aaf slot` của agent bị giết thì khe trống ngay). File trong `guest/` chỉ được mở khi là file thường, một tên, không qua symlink, tối đa 1 MiB. Số đo RAM của khách ghi vào `guest/heavy_stats.json`, chỉ khách đọc; bản ghi tạm dừng của khách (`guest/paused.<pgid>`) chỉ khách quét. Khe mà khách không thấy file khoá (trần cấu hình lớn hơn số CPU) thì với khách coi như không có.
- Chuyển tiếp từ bố cục cũ (`locks/heavy.<n>.lock`, `locks/drain.lock`; `throttle::legacy`): `aaf` mới coi khe là bận khi file khoá cũ của khe đó đang bị khoá hoặc còn ghi một lệnh mồ côi đang chạy, đọc giữ chỗ và token của người giữ cũ từ file cũ, và tôn trọng `drain.lock` cũ. Chỉ một chiều: `aaf` cũ không nhìn `throttle/`, nên không thấy người giữ mới; và khách không đọc được `locks/`, nên với khách khoá cũ coi như trống. `heavy_stats.json`, `locks/paused.<pgid>` và khoá của stats ở nguyên chỗ cũ, không cần chuyển.
- Chờ vì tải không phải lỗi: `aaf gate` in tiến độ chờ ra stderr; factory không chuyển task sang `Blocked` và không tính vào unblock cycle.
- API: `gate::run_gate_with(data_dir, repo_root, cfg, mode, clock, machine: &MachineConfig)`; `gate::run_gate_in` giữ chữ ký cũ và gọi với `MachineConfig::default()`. Thời gian chờ và cờ `degraded` ghi vào `reasons` của receipt (không đổi schema, không đổi status). `Throttle::run_slot(data_dir, clock, &SlotJob)` là đường vào của `aaf slot`: cùng `Throttle`, nhận argv thay cho `sh -c`, stdio của bên gọi, `wait_limit_secs`.
- Gom gate ở factory: task xong phần agent vào hàng chờ gate và nhả worker (agent của task khác chạy tiếp). Mỗi repo một luồng gate: lấy MỌI task đang chờ của repo, gộp các nhánh `aaf/<task>` vào một worktree tích hợp trên base, gate một lần. `Clear` ⇒ cả lô qua. Đỏ ⇒ chia đôi lô và gate lại từng nửa cho tới khi cô lập được task gây đỏ (lô 1 task đỏ ⇒ task đó đi thang unblock); nhánh xung đột khi gộp ⇒ gate riêng. Lô 1 task thì gate thẳng worktree của task. Hàng chờ càng dài thì lô càng lớn, số lượt build không tăng theo số task.

## E. Nghiệm thu (chạy thật, không chỉ fixture)

1. `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`: exit 0, số test > 0. Lượt chạy dùng làm bằng chứng đặt `AAF_REQUIRE_REAL=1`: test của `aaf-cli` chạy lệnh nặng qua binary thật (`cli_gate`, `cli_gate_orphan`, `cli_slot`, `cli_slot_nested`, `cli_slot_signal`) bình thường tự bỏ qua và in `SKIPPED …` ra stderr khi áp lực bộ nhớ khác Normal; với biến này chúng thất bại thay vì báo `ok` mà không chứng minh gì. Biến không đụng tới các test sandbox tự bỏ qua khi máy không có `sandbox-exec`.
2. Hook thật: cài vào một repo tạm bằng `aaf init`, một phiên `claude -p` thật thử `git push --force` ⇒ bị chặn; dán dòng output.
3. `aaf gate --release --json` chỉ-đọc trên các repo app thật có trên máy: liệt kê mọi CRITICAL và soát tay, yêu cầu 0 false-positive.
4. `aaf accounts list --json` thấy đúng các profile thật.
5. `aaf doctor --json` trên máy này.
6. P2: một task thật chạy hết `aaf run` trong repo tạm (worktree → agent → gate → nhánh + receipt). Repo tạm phải commit `.claude/settings.json` trước, nếu không task bị chặn trước khi agent khởi động (§C.3).
Mục nào chưa chạy thật được thì báo "chưa nghiệm thu thật — lý do", không gọi là xong. Trạng thái từng mục sau Wave 3 (đã chạy thật gì, chưa chạy gì) nằm ở bảng "Trạng thái" của `docs/README.vi.md`.
